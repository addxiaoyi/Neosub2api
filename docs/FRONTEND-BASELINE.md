# 前端基准与红线

本文件是 `apps/web/` 所有改动的裁决依据。它不描述「我们想要什么样的前端」，只固定「前端必须长成什么样」。后续任何会话、任何提交，先读这一页，再动 `apps/web/`。

## 1. 基准来源

- 上游仓库：`https://github.com/addxiaoyi/codebuddy2api`，取其中的 `web/` 目录。
- 本仓 `apps/web/` 是该目录的迁移产物。**迁移目标 = 原样**，不是「迁移后趁机优化」。
- 基准锁定的内容，一律以上游代码为准，不以本仓任何文档、提案、原型为准：

| 类别 | 以基准为准的判定点 |
| --- | --- |
| 页面结构 | `app/` 路由、每个页面的分区顺序、卡片与表格的排布、详情抽屉的层级 |
| 组件 | 组件划分与命名、shadcn 组件选型、图标来源与尺寸、交互形态（Sheet / Dialog / Toast） |
| 配色 | 背景、表面、边框、主色、危险色、徽章底色，含浅色与深色两套 |
| 字号与度量 | 字号阶梯、行高、间距、圆角、容器最大宽度、栅格断点 |
| 底部导航 | 样式、项数、图标、顺序、移动端行为 |
| i18n | `lib/i18n/locales/*.json` 的键名、嵌套结构、既有文案 |
| 布局 | `app/layout.tsx`、`app/(main)/layout.tsx`、顶部栏与内容容器 |

判定规则：拿不准时，去读基准仓库对应文件；读不到再提问，不要凭印象补。

比对报告里必须写明所用基准 commit 的短 hash，避免「基准漂移」导致两次结论互相打脸。

## 2. 允许的改动（白名单）

只允许「让多 provider 接入成立」所必需的配置抽象与后端字段对接。白名单之外一律先批准、再动手。

| 允许项 | 具体范围 | 边界 |
| --- | --- | --- |
| provider 元数据抽象 | 把写死在页面里的 provider 列表收进 descriptor / 配置模块；渲染仍用原来的表格与卡片 | 不新增页面、不新增视觉组件、不改列结构与顺序 |
| 后端字段对接 | 新增 provider 的字段、状态、错误码映射、能力开关，接到既有 UI 槽位上 | 不因字段而改布局，不加第二套状态表达 |
| 类型与适配层 | 新 provider 的类型定义、响应归一化、adapter | 不侵入组件内部渲染逻辑 |
| i18n 新增 | 只允许**新增**键（新 provider 名称、新错误码文案），并同步全部 locale | 不改既有键名与键值，不删键 |
| 复用既有原语 | 加载 / 空 / 错误 / 确认弹窗沿用现有实现 | 不为新场景另造一套 |

白名单的判定标准：改动完成后，用基准数据渲染，页面的 DOM 结构与视觉应和基准一致；只有 provider 相关数据不同。

## 3. 明确禁止

以下行为在评审中按阻断处理，不接受「先合入再补」：

- 自造设计系统：`tokens`（`app/tokens.css` 之类）、`AppShell`、`components/shell/`、`components/states/`、`provider-kit/` 等一整套新抽象。
- IA 重设计：改导航分组、改页面清单、改入口数量、把底部 dock 换成侧栏。
- 品牌改名：`渡口`、`Ferry` 及任何同类替换。
- 删除原有 tab 或页面入口（例如 `/settings` 的「服务商接入」tab）。
- 替换导航样式：dock 的形状、位置、动效、激活态。
- 新增页面、新增视觉组件、新增全局样式文件。
- 改配色、字号阶梯、间距、圆角、阴影。
- 把 `docs/design/prototype.html` 的样式拷进 `apps/web/`。
- 以 `/design` 演示页作为可交付页面（它不在产品页面清单内）。
- 以本仓新写的文档（含 `FRONTEND-SKELETON.md`）作为基准依据。

入口数量的判定口径（2026-11-04 登记）：本节「改入口数量」「新增页面」约束只针对**未经批准的新增**；已批准并登记在 §4 现状备注（2026-11-04）的自加入口——设置页 `runtime` tab 与导航 `quota`、`pricing` 两项——不计入阻断范围，后续基线审查按此口径判定，不再重复询问。

## 4. 校验方法

每次动 `apps/web/` 后，按同一流程出证据，不接受口头「看起来一样」。

1. 拉基准仓库，进 `web/`，按它的 README 安装与构建，本地起服务。
2. 本仓构建 `apps/web/`，本地起服务；两套用同一份数据、同一登录态、同一语言。
3. 逐页截图，两档视口各一遍：`1440` 宽与 `768` 宽。页面清单以 `app/(main)/` 下的路由为准：

| 组 | 路由 |
| --- | --- |
| 入口 | `/`（登录 / 引导）、`/(auth)` |
| 主页面 | `/dashboard`、`/accounts`、`/quota`、`/pricing`、`/keys`、`/models`、`/playground`、`/stats`、`/logs`、`/security`、`/settings`（服务商配置在设置页「服务商」tab，不再有独立 `/providers` 页） |
| 不计入 | `/design`（演示页） |

现状备注（2026-11-03）：`/red-packets` 与 `/claim` 已按业务决定整条链路删除（后端从无端点），基准不再保留这两个页面，也不应再补；`/tasks` 页面与相关 9 条幽灵路径（签到记录 / 任务日志 / 上游日志 / 任务执行 / 认领计划）已整体删除，页面清单与导航均不再包含它；`/providers` 页已并入设置页，导航与路由以当前 `ManagementBar.tsx` 为准。

现状备注（2026-11-04，已批准的自加入口）：设置页现有 8 个 tab，顺序为「上游配置 → 运行参数 → 模型映射 → 管理用户 → 访问令牌 → 系统更新 → 更新日志 → 关于」；其中 `runtime`（运行参数：影响网关运行时行为的非密钥配置，存库即时生效，含 JSON 导出 / 导入；仅管理员可见，非管理员下为 7 个 tab）为本项目自加，基准设置页 7 个 tab 无对应项，已批准保留。导航现有 11 项（基准 9 项），其中 `quota`（配额管理：sub2api 订阅账号池的分组、账号与扣减流水）与 `pricing`（定价：价格表与干跑解析）为本项目自加，基准无对应页面，已列入上方页面清单。以上均为已批准的自加入口，非越界改动，判定口径见 §3 末尾。

4. 逐页比对：同视口、同页面、同数据。差异按条记录，一条一行：

| 页面 | 视口 | 差异 | 是否白名单内 | 理由 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 例：`/providers` | 1440 | 多出第 12 家 provider 行 | 是（配置抽象） | 新增 provider 接入 | 接受 |
| 例：`/providers` | 768 | 表格右缘被裁切 | 否 | 布局漂移 | 必须修复 |

5. 结论规则：白名单外的差异，要么修到与基准一致，要么等明确批准后重写本文件；两张截图之间不能既不改也不记。
6. 证据留存：截图放 `docs/ux-shots/baseline/<日期>/`，比对表贴进提交说明或评审记录。

## 5. 三条历史教训

1. **两次把「自造骨架」当成基准。** `FRONTEND-SKELETON.md` 里的 tokens、AppShell、states、provider-kit 是本仓新造的抽象，却被当成前端应有的样子推进了两轮。基准只能来自上游 `web/` 的代码，不能来自本仓新写的方案文档。
2. **把 `/design` 演示页误当成果。** 原型与演示页只表达设想，不是产品页面；验收清单里没有它，截图对比也不包含它。
3. **把 IA 提案当成已批准。** `docs/design/ia-proposal.md` 是未采纳提案，导航与页面结构一律以基准为准；任何 IA 级改动必须单独批准，并先改本文件。

## 6. 冲突处理

优先级：上游基准代码 > 本文件 > 本仓其它文档 > 会话里的临时假设。

碰到「基准与现状不一致」时，先记差异，再问是否允许修；不要顺手把现状「优化」成自己觉得更好的样子。不确定就停手。
